# Сборки Pake под macOS, Windows и Linux через GitHub Actions

## Что дает GitHub Actions

GitHub Actions позволяет запускать сборку на временных виртуальных машинах GitHub. Для этого не нужны собственные компьютеры с Windows или Linux:

- `macos-latest` собирает macOS-приложение;
- `windows-latest` собирает Windows-приложение;
- `ubuntu-latest` собирает Linux-приложение.

Разработчик работает с GitHub с любого компьютера, включая Mac: отправляет код, запускает workflow и скачивает готовые артефакты.

Сборка Windows не выполняется непосредственно на Mac. Mac только отправляет код и команду запуска, а компиляция происходит на временном Windows runner в GitHub.

## Результаты сборки

Рекомендуемый минимальный набор:

| Платформа | Runner | Артефакт | Назначение |
| --- | --- | --- | --- |
| macOS | `macos-latest` | `.dmg` | Установка на macOS |
| Windows | `windows-latest` | `.msi` | Установка на Windows x64 |
| Linux | `ubuntu-latest` | `.deb` | Debian, Ubuntu и совместимые системы |
| Linux | `ubuntu-latest` | `.AppImage` | Переносимый пакет для разных Linux-дистрибутивов |

Pake также принимает Linux targets `rpm` и `zst`, но текущая проверенная конфигурация `pake-cli` по умолчанию выпускает `deb` и `appimage`. Поддержку `.rpm` и `.zst` следует добавлять и проверять отдельно.

## Что уже есть в Pake

В локальном репозитории Pake есть готовая основа:

- `.github/workflows/single-app.yaml` в `pake-cli`;
- матрица `linux`, `macos`, `windows`;
- Linux-команда с `--targets deb,appimage`;
- Windows-команда с `--targets x64`;
- macOS-команда с `--targets universal --multi-arch`;
- загрузка результатов через `actions/upload-artifact`;
- публикация файлов в GitHub Release при сборке по git tag.

Этот workflow можно взять за основу для отдельного репозитория приложения `ru.1forma.ru`. Перед использованием его нужно согласовать с проектным pipeline: локальная macOS-сборка здесь отдельно собирает `.app`, отдельно упаковывает `.dmg` и отдельно выполняет notarization.

## Рекомендуемая структура репозитория

В GitHub должны находиться:

```text
.github/
  workflows/
    build-all-platforms.yml
projects/
  ru.1forma.ru/
    config.json
    same-window-routes.js
    scripts/
pake-cli/
```

Если `pake-cli` и приложение остаются разными репозиториями, workflow приложения должен явно:

1. скачать репозиторий приложения;
2. скачать нужную ветку или зафиксированный commit `pake-cli`;
3. установить Node.js, pnpm и Rust;
4. собрать CLI из исходников;
5. запустить платформенную сборку приложения;
6. загрузить артефакты.

Для воспроизводимости лучше фиксировать commit или tag `pake-cli`, а не всегда собирать случайное текущее состояние основной ветки.

## Как запускается сборка

### Ручной запуск

Workflow должен поддерживать `workflow_dispatch`. После отправки workflow в GitHub:

1. открыть репозиторий;
2. перейти в `Actions`;
3. выбрать `Build all platforms`;
4. нажать `Run workflow`;
5. дождаться завершения трех jobs;
6. скачать артефакты со страницы запуска.

Через GitHub CLI тот же запуск выглядит так:

```bash
gh workflow run build-all-platforms.yml
gh run list --workflow build-all-platforms.yml
gh run watch
gh run download
```

### Релиз по тегу

Workflow можно запускать при публикации тега:

```bash
git tag v0.1.0
git push origin v0.1.0
```

После успешной сборки `.dmg`, `.msi`, `.deb` и `.AppImage` прикладываются к GitHub Release.

## Доступ к GitHub

Рекомендуемая схема на локальном Mac:

- SSH-ключ используется для `git clone`, `git pull` и `git push`;
- GitHub CLI используется для управления Actions и артефактами;
- авторизация GitHub CLI выполняется локально командой `gh auth login`;
- секреты добавляются в `Settings -> Secrets and variables -> Actions`.

Токены, приватные SSH-ключи, сертификаты и пароли нельзя хранить в репозитории или передавать в исходном коде workflow.

## Подпись и публикация

### macOS

Для распространения без предупреждений Gatekeeper нужны:

- сертификат Developer ID Application;
- Apple Developer Team ID;
- credentials для notarization;
- подпись приложения;
- notarization;
- stapling результата.

Значения хранятся в GitHub Actions Secrets. Текущий проектный контракт требует отделять сборку `.app`, упаковку `.dmg` и notarization.

### Windows

Неподписанный `.msi` можно собрать без сертификата, но Windows SmartScreen может показывать предупреждение. Для публичного релиза желательно добавить code-signing certificate и подпись установщика.

### Linux

Для обычной сборки `.deb` и `.AppImage` сертификат не требуется. Для публикации через официальный APT/RPM-репозиторий понадобится отдельная подпись пакетов и metadata репозитория.

## Стоимость

- Для публичных репозиториев стандартные GitHub-hosted runners обычно доступны бесплатно.
- Для приватных репозиториев действует включенная в тариф квота минут и хранилища.
- После исчерпания квоты дальнейшие запуски могут требовать настроенного биллинга.
- Актуальные лимиты нужно проверять в GitHub Billing перед включением регулярных сборок.

## Ограничения и проверки

- Каждая платформа должна собираться на runner соответствующей ОС.
- Успешная macOS-сборка не подтверждает работоспособность Windows и Linux версий.
- Pake использует WebView2 на Windows и WebKitGTK на Linux, поэтому поведение сайта и разрешений нужно проверять отдельно на каждой ОС.
- `.deb` следует проверять как минимум на поддерживаемой версии Ubuntu.
- `.AppImage` следует проверять отдельно: его наличие не гарантирует работу на любом Linux-дистрибутиве.
- Временные artifacts GitHub Actions имеют срок хранения; релизные файлы лучше публиковать в GitHub Release.

## План внедрения для `ru.1forma.ru`

1. Определить GitHub-репозиторий, где будут лежать приложение и workflow.
2. Зафиксировать версию или commit `pake-cli`.
3. Добавить `build-all-platforms.yml` с матрицей трех ОС.
4. Перенести project-specific injections и параметры Pake в команды каждой job.
5. Сначала собрать неподписанные тестовые артефакты.
6. Проверить запуск приложения на Windows, Ubuntu и macOS.
7. После функциональной проверки подключить подпись Windows и macOS.
8. Добавить сборку по тегу и публикацию GitHub Release.

До прохождения проверки на реальных Windows и Ubuntu артефакты следует считать тестовыми, а не релизными.
